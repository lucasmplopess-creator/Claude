Explaining a Technical Problem to a Non-Technical Person

"Separate the Symptom From the Cause"

Non-technical stakeholders usually only see the symptom, the app was slow, the report was wrong, and technical explanations that jump straight into cause-level detail (server configs, database indexes) lose them immediately.

A structure that works well in English: name the symptom in plain terms first ("the checkout page was loading slowly for about twenty minutes"), then the root cause in simplified language ("that happened because one of our servers was handling more traffic than it could manage"), then the fix, including any workaround already in place.

It's also worth naming what's still uncertain honestly: "we've patched it for now, but we're still investigating the root cause to prevent it from happening again" is far more reassuring than pretending the fix is fully understood when it isn't.

ETAPA 5Gramática de Apoio Aplicada à ConversaçãoGrammar for Conversation

Explicar problemas técnicos depende de conectores de causa e efeito e de estruturas de definição do problema.

EstruturaExemplo (EN)Tradução (PT)
The issue is that...The issue is that one server was overloaded.Estrutura direta para nomear o problema central, sem rodeios.
This happens because...
(causa)		This happens because the database wasn't indexed correctly.Conecta um sintoma observado à sua causa técnica, de forma simples.
Think of it like...
(analogia, reforço)		Think of it like one cashier trying to serve a whole line alone.Reforça a explicação com uma analogia acessível, reutilizando a estrutura do Tema 58.

Dica prática: sempre nomeie o sintoma antes da causa ("the issue is that X happened, because Y"), invertendo essa ordem, o público não técnico perde o fio da explicação rapidamente.

ETAPA 6Speaking: Perguntas AbertasOpen-Ended Speaking

Responda em voz alta, gravando se possível. Não vale responder em uma frase só: use o que você escreveu na Etapa 4 como base, mas fale livremente.

  1. Describe a technical problem you'd need to explain to a non-technical stakeholder.
  2. What's the difference between the symptom and the root cause in that situation?
  3. What analogy could make the root cause of that problem easier to understand?
  4. How do you communicate uncertainty honestly when you haven't found the root cause yet?
  5. What's a time a non-technical explanation you gave really landed well?
  6. How do you avoid jargon creeping into a technical explanation without noticing?
  7. What's the risk of oversimplifying a technical problem to a stakeholder?
  8. How do you explain a workaround without it sounding like the problem isn't serious?
  9. What's an edge case you've had to explain that confused people at first?
  10. How do you handle a stakeholder who keeps pushing for more technical detail than needed?

Expressões úteis para esta conversa:

  • "The issue is that...", para nomear o problema com clareza.
  • "This happens because...", para conectar sintoma a causa.
  • "We've patched it for now, and...", para comunicar solução temporária.
  • "Think of it like...", reforço de analogia.
